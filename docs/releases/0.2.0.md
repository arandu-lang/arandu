# Arandu 0.2.0 — relatório de promoção

**Estado:** preparação; nenhuma tag foi criada.

**Canal:** release do SDK Arandu, série 0.2.x (motor quente).

O PR de preparação deve ser mergeado e ficar integralmente verde antes da tag.
Depois, execute na `main` atualizada:

```bash
git switch main
git pull --ff-only origin main
cargo run --locked -p xtask -- check-release-contract v0.2.0
git tag -a v0.2.0 -m "Arandu 0.2.0"
git push origin v0.2.0
```

Não mova nem force a tag. O workflow exige o S0 verde do PR mergeado e executa
somente as provas exclusivas de empacotamento, publicação e instalação pública.

## Escopo

A 0.2.0 entrega o motor quente (HOT.1–6 no
[roadmap](../arandu-compiler-roadmap-v0.1.md#02x--motor-quente-e-imagem-dev))
para builds nativos de desenvolvimento com Cranelift em Linux x86-64 ELF. O
contrato está na
[RFC 0011](../rfcs/0011-incremental-partitioned-aot-and-in-process-linker.md)
§8; a arquitetura de queries, na
[arquitetura Salsa/LSP](../arandu-salsa-lsp-architecture-v0.1.md); a
metodologia e os resultados, em [benchmarks](../benchmarks/README.md).

- **Sessão viva (HOT.2).** O CLI mantém a DB entre builds; o refresh lê só as
  entradas cujo stamp mudou ou caiu na janela "racy". Toolchain, target,
  opções, stdlib, conjunto de fontes ou manifesto diferentes reabrem a sessão.
- **Daemon por projeto (HOT.3).** `arandu build` fala com um daemon local
  (socket 0600 com credenciais do par verificadas, identidade por
  executável/versão/variáveis de build), que coalesce pedidos, cancela um
  build superado antes da publicação e recicla por RSS. Qualquer falha cai no
  batch; `--no-daemon`, `ARANDU_DAEMON=0` e `CI` definida usam batch.
- **Imagem dev (HOT.4).** Cada função ocupa um slot com folga (~1,25×, classes
  de 16 bytes); uma edição que mantém a classe é aplicada in-place no
  executável publicado, e o clean build reproduz o mesmo layout byte a byte.
  Saídas derivadas validadas por conteúdo são escritas sem `fsync`.
- **Recuperação (HOT.5).** Kill, socket quebrado, cache adulterado ou build
  interrompido levam a rebuild verificado, nunca a reutilizar estado não
  revalidado. Os fingerprints registrados de um build são os do texto que ele
  compilou, mesmo quando o arquivo é salvo durante o build.
- **Medição (HOT.1/HOT.6).** `xtask bench-incremental` mede oito classes de
  edição com p50/p95, CPU, RSS, caminho de publicação e delta de bytes por
  função lido do código antes do padding (`code_bytes` nos sidecars de CGU),
  com `--daemon` para o caminho real. Endurance: 1000 edições pelo mesmo
  daemon com RSS e filas limitados.
- **Invalidação por item (RFC 0042).** Itens são tipados e baixados em
  coordenadas relativas ao próprio item (`AstId`, `ItemPlacement`); um corpo
  que cresce não reexecuta a tipagem nem o lowering dos itens que desloca, e
  importadores observam só a superfície de declaração do arquivo.

Resultado no host de desenvolvimento (corpus medium, release, pelo daemon):
edição de corpo privado de 258/314 ms (p50/p95, 2026-10-28) para 64/83 ms na
melhor sessão, noop de 15,5/22,5 ms para 3,8/6,0 ms. A tabela completa e a
variação entre sessões estão em [benchmarks](../benchmarks/README.md).

## Mudanças incompatíveis

- **Faixa de toolchain dos projetos 0.1.x.** `arandu new` da 0.1.x grava
  `arandu = ">=0.1.0-rc.4, <0.2.0"` em `[toolchain]`, e a 0.2.0 recusa esses
  manifests como incompatíveis. Atualize a faixa para `">=0.2.0, <0.3.0"`
  depois de revisar as mudanças abaixo. Projetos novos recebem a faixa da
  versão do toolchain que os criou, até a próxima versão que pode quebrá-los.
- **Grafias legadas de anotações removidas (RFC 0002).** `@no_fallback`,
  `@no_generational_fallback`, `@link`, `@FfiExport`, `@unsafe`, `@effects`,
  `@nosuspend`, `@specialize` e `@repr` deixam de ser aceitas. A linha 0.1.x
  avisou cada uma com `W008`, agora reservado; na 0.2.0 elas são anotações
  desconhecidas (`N012`) e não aplicam semântica. O diagnóstico nota a
  renomeação e traz replacement estruturado para o nome canônico, que o quick
  fix do editor aplica; o hover de uma grafia removida aponta o nome canônico.
- **`module` precisa corresponder ao arquivo (`N020`).** Num pacote, um arquivo
  sob a raiz de fontes é o módulo `<pacote>.<caminho>`; declarar outro caminho
  é erro, e a entrada só pode declarar o nome do pacote. Módulos sem
  declaração recebem o nome derivado das raízes do pacote, o que corrige a
  colisão de funções privadas de mesmo nome em módulos diferentes (ICE no
  Cranelift, definição duplicada no `ld`, na JIT e no LLVM).
- **Símbolo nativo duplicado (`N021`).** Duas funções cujos nomes qualificados
  coincidem são rejeitadas antes do codegen, em vez de falhar no backend ou no
  link.
- **Borrow promovível guardado em memória (`O004` erro).** A promoção
  geracional implícita de um borrow `Copy` gravado num campo ou através de
  outra referência escrevia um handle num slot tipado como referência; toda
  releitura devolvia os bits do handle (Cranelift JIT/AOT e LLVM) ou gerava C
  inválido. Esses escapes agora são erro e a promoção implícita saiu do
  pipeline (emenda na RFC 0001). Handles explícitos (`GenArena`/`GenRef`)
  continuam iguais.

## Correções

- **Texto de `f64` no Wasm (WASM.FLOAT).** O `ToStr` de floats no backend Wasm
  imprimia até 15 dígitos significativos com aritmética de ponto flutuante, e
  divergia do runtime em valores como `0.1 + 0.2`. Agora escreve o mesmo texto
  que o runtime: o decimal mais curto que volta ao valor, em notação
  posicional, pelo algoritmo exato que o `flt2dec` do Rust usa como
  referência. A função auxiliar só entra em módulos que formatam float (~1,9
  KB); cada formatação custa ~64 B de código, contra ~580 B antes.
- **Vazamento na JIT/AOT do Cranelift (AGG.1).** Agregados `Copy` que
  carregam uma view, como o `Option<ref T>` de `slice.get`, eram alocados por
  execução e nunca liberados; `GenArena.getRef` perdia ~225 bytes por
  chamada. Eles agora ficam no armazenamento da invocação, como os demais
  agregados admitidos. Funções que retornam `ptr` ou `ref` deixam de alocar
  seus temporários por chamada quando não tomam o endereço do próprio
  armazenamento (análise de escape no AMIR). Os endurance AGG.1 têm RSS
  estável em C e na JIT.
- **Default de campo de struct importada.** `lib.Point { x: 1 }` com um
  default declarado em outro arquivo estourava a pilha do compilador: o
  importador lia a expressão default no próprio pool. O default agora é baixado
  do item que o declara.
- **Funções importadas no DWARF e nos diagnósticos** apontam para a própria
  declaração, não para o `import`.
- **Backend LLVM.** Payload escalar de enum lido com o tipo do campo e
  literais `char` com barra invertida decodificados como escalar, dois ICEs
  achados pelo fuzzing (`check-fuzz-regressions`).
- **Falhas de build na sessão** retornam ao chamador em vez de encerrar o
  processo, o que mantém o daemon vivo depois de um erro de compilação.

## Limites conhecidos

- O gate de p95 ≤ 100 ms em edição de corpo não foi certificado num host de
  referência: o harness mede, mas o resultado varia entre sessões do host de
  desenvolvimento (p95 de 83 a 134 ms). Por decisão do mantenedor, a 0.2.0
  registra a latência sem impô-la como limite.
- macOS e Windows fazem link completo; Windows usa batch (sem named pipes).
- Um `let` novo num corpo não rebaixa importadores, mas retipa os itens do
  próprio arquivo (~2,5× uma edição de mesmo tamanho); os locais relativos ao
  item ficam para a 0.7.x (RFC 0042 §8.13).
- Mudança de assinatura pública reexecuta as units do fechamento transitivo de
  declarações (~1,2–1,9 s no medium); corte no chamador direto é 0.3.x.
- Resultados de ponteiro bruto e referências sem resumo provado que tomam o
  endereço do próprio armazenamento, e carriers de views no Wasm, ainda usam
  a alocação legada (ABI/layout).
