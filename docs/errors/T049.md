# Error T049: Invalid FFI Export

`@Export` publishes a function to the linker with a flat C symbol and the
target's C calling convention. The compiler only accepts signatures whose
representation at the binary boundary is fixed by the C ABI, so a C caller can
never disagree with the generated code about parameter or return layout.

Accepted parameters and return types:

- fixed-width integers: `i8`, `i16`, `i32`, `i64`, `u8`, `u16`, `u32`, `u64`;
- `f32` and `f64`;
- `bool`;
- raw pointers such as `ptr Frame`;
- `void` as the return type only;
- `Result<T, E>` as the return type, lowered to a C status code plus an
  out-parameter (see below).

Everything else is rejected at compile time.

## Widths and aliases

`int` and `uint` are fixed 32-bit values in Arandu (RFC 0023), so they cross as
`int32_t`/`uint32_t` on every target. `isize`/`usize` follow the target pointer
width and cross as `int32_t`/`int64_t` and `size_t`; `float` is `double`.
Fixed-width types are still preferable for an ABI that must stay stable when
the target changes:

```arandu
@Export
func checksum(data: ptr u8, len: u32): u32 {
    return len
}
```

`char` is rejected: it is a Unicode scalar value, not a C character. Use `u32`
or `u8` when the boundary expects a code unit.

## Buffers and strings

Slices (`[]T`, `mut []T`) and `str` cross as a `(ptr, len)` pair, with the
length in elements for slices and in bytes for `str`. The generated typedefs
keep mutability and text distinct:

```c
typedef struct { const uint8_t *ptr; size_t len; } AranduSliceU8;
typedef struct { uint8_t *ptr; size_t len; } AranduMutSliceU8;
typedef struct { const uint8_t *ptr; size_t len; } AranduStr;
```

`AranduStr` is UTF-8 and is **not** NUL-terminated; `Arandu` does not validate
the encoding at the boundary. A C consumer that needs a C string must copy it.

## Nominal types by value

Structs annotated with `@Repr("C")` are exported by value. Their layout and
parameter class come from `LayoutEngine` and the target ABI classifier, so
`byval`, register splitting and padding are the same on the call and definition
sides. The generated header repeats the layout as `_Static_assert`s:

```arandu
@Repr("C")
public struct Frame {
    id: u32
    weight: f32
}

@Export
func frameId(frame: Frame): u32 {
    return frame.id
}
```

An opaque pointer (`ptr Frame`) remains the right tool when the type is a
handle whose fields the C side must not see. The header then emits only
`typedef struct Frame Frame;`: the fields are never spelled, so a handle may
hold runtime-only fields (a `Vec`, a generator) that could not cross by value.

The header also carries the doc comments (`///`) of exported functions and
opaque types as C block comments. When an exported `@Destructor` is associated
with the type, the `typedef` and any function returning `ptr Frame` document
the release function; without one, the return comment says so explicitly.
These notes describe the existing ownership contract; a missing destructor is
never an error.

## Results across the boundary

C has no sum types and no exception channel, so an exported `Result<T, E>` is
rewritten into the shape every C SDK already uses — a status code plus an
out-parameter (`HRESULT`, `VkResult`, `GError`):

```arandu
@Export
func read(v: u32): Result<u32, u32> {
    if v == 0 as u32 {
        return Result.Err(7 as u32)
    }
    return Result.Ok(v + 1 as u32)
}
```

```c
/* Status code: 0 on success, non-zero on failure. */
uint32_t read(uint32_t, uint32_t *);
```

`Ok` becomes status `0`; `Err(e)` becomes the status itself. When `T` is not
`void` the value is written through a trailing `T *out` parameter, and the
header documents the convention. With `Result<void, E>` no out-parameter is
added. The rewrite happens once in AMIR, so it applies to every backend and the
header is derived from the same signature.

`E` must be a fixed-width integer (`i8`–`i64`, `u8`–`u64`): a status is
compared by the C caller and cannot change width with the target. `int`,
`usize` and non-integer error types are rejected. `Ok` must carry a value
unless `T` is `void`.

Two further restrictions keep the boundary honest:

- every `return` must construct `Result.Ok(..)` or `Result.Err(..)` directly;
  returning a `Result` stored in a local is rejected rather than guessing
  which status it holds;
- an exported `Result` function cannot be called from Arandu, because its
  signature changes at the boundary and an in-language call would silently see
  the status instead of the sum type. Keep the logic in an internal function
  returning `Result` and export a thin wrapper, or export a wrapper that takes
  `out: mut ref T`.

A `@Destructor` cannot return `Result`: `T035` already requires the release
function to be `void`, and failure is reported through a separate status
function.

## Callbacks

A C callback parameter (`void (*)(...)`) has no supported Arandu type yet.
Function types such as `(u32) -> u32` exist and a function name is a value,
but calling through that value is rejected with `T033`: Arandu only performs
direct calls. Exporting a callback therefore needs first-class function calls
in AMIR and in every backend (RFC 0032), not just a header `typedef`.
Until then, a C consumer that needs to observe Arandu must poll a state accessor
or call an exported function per event; handing C a function pointer that
Arandu cannot invoke would compile and then fail at runtime.

This is a decision for 0.1.11, not an omission: callbacks stay rejected until
the staged path recorded in RFC 0030 (§3.2.2) lands — a non-capturing
`extern "C"` function-pointer type, one indirect-call operation shared by every
AMIR visitor and backend, and only then callback parameters in `@Export`.
Capturing closures never cross the boundary; C receives context as an explicit
`ptr[u8]` user-data argument.

## Symbol names

`@Export` publishes into the single C namespace, so the effective name (the
argument, or the function name without one) is rejected when it:

- is a C23 or C++23 keyword (`int`, `delete`, `class`, …): the generated header
  is valid C and is also wrapped in `extern "C"` for C++ consumers;
- is reserved to the C implementation (`__name`, `_Name`);
- starts with `ar_`, the namespace of the Arandu runtime (`ar_rt_*`,
  `ar_str_concat`, synthesized `ar_thread_capture_*`), where an export would
  interpose on, or collide with, the host runtime at link time;
- is `main`, which belongs to the program entry point.

An `@Export` in an imported module of the package is published exactly like
one in the entry file: it keeps external linkage and appears in the header.
Two modules exporting the same name are rejected when the program is
assembled, before any object or header is written:

```text
error[T049]: exported symbol 'shared' is claimed by two functions; C has a
single namespace, so give one of them a distinct `@Export("...")` name
```

## Component Model names

A WebAssembly component exports the `public` functions of the root module and
every `@Export`; public API of imported modules and the stdlib stays internal.
WIT identifiers are lowercase kebab-case and share one namespace per interface
(types and functions) and per record, enum or variant. Distinct Arandu names
that lower to the same identifier are rejected before encoding:

```text
error[T049]: `Vec3` and `vec3` both export as `vec3` in the component
interface `exports`
```

Rename one of them, or keep the helper private.

## Integer extension

`bool`, `u8`/`byte` and `u16` cross as `zeroext`, `i8` and `i16` as `signext`,
on parameters and returns, exactly as `clang -target` emits them. AAPCS32 and
the RISC-V psABI make the callee widen a sub-word return to a full register,
and C callers rely on it, so `uint8_t narrow(uint32_t)` returns a value with
the upper bits cleared on every target.

## Shape restrictions

An exported function must have a body. It cannot be `async` or generic: those
need a monomorphized or coroutine-specific entry point that `@Export` does not
synthesize. Methods are rejected because C has no receiver convention, with one
deliberate exception: an `@Destructor` is the release function of its type, so
it exports as `void name(T *self)`. That is the whole ownership contract — C
never spells the handle's fields, and `TypeInfo::destructors` decides which
symbol releases it. Give the symbol an explicit name when the C side expects a
prefix:

```arandu
@Export("arandu_core_process_inputs")
func processInputs(raw: u32, mode: u32): u32 {
    return raw
}
```

Two exported functions cannot claim the same symbol; the second declaration is
rejected instead of silently replacing the first one at link time.

## Freestanding targets

On a target without an operating system (`thumbv6m-none-eabi`,
`thumbv7em-none-eabihf`, `riscv32imc-unknown-none-elf`) an exported function
must be self-contained. The packaged host runtime provides the allocator,
fat-string helpers, generator tables and the coroutine scheduler; none of them
exist in a bare-metal image. If any function reachable from an `@Export` needs
one of those symbols, the build fails instead of producing an object that only
breaks when the C linker runs:

```text
error[T049]: exported function 'decorate' needs the host runtime
(ar_jit_i64_to_str, ar_str_concat) which target 'thumbv6m-none-eabi' cannot
provide; keep the exported path free of allocation, strings, generators and
coroutines
```

Calls to symbols the firmware supplies, such as the Pico SDK or a `#[no_mangle]`
C function, are not host runtime and stay allowed.

The check covers the Arandu host runtime only. LLVM itself may lower block
copies and wide arithmetic to compiler-builtins calls (`memcpy`, `memset`,
`__aeabi_uldivmod`, `__mulsi3` on targets without the instruction); the
firmware link supplies them, typically from `compiler-rt`/`libgcc`, as for any
freestanding C object. Objects are built with the LLVM toolchain: RISC-V uses
the `riscv32-unknown-none-elf` triple with `-march=rv32imc -mabi=ilp32` (clang
has no `riscv32imc` architecture in its triple parser), and `--linker-script`
links with `ld.lld`.

## Aggregates across the boundary

A `@Repr("C")` struct, a synchronous slice (`[]T` / `mut []T`) or a `ptr T`
crosses the boundary in the shape the target C ABI prescribes, not in Arandu's
in-memory representation:

- System V AMD64: eightbytes merge into `iN` (exact widths such as `i24` or
  `i56`), `{ i64, i32 }` for mixed lanes, `byval`/`sret` above 16 bytes.
- Windows x64: only 1, 2, 4 and 8 byte aggregates travel in a register.
- AAPCS64: homogeneous float aggregates stay in vector registers, up to 16
  bytes travel in `x0`–`x7`.
- AAPCS32: composites split into 32-bit words; hard-float targets keep
  homogeneous float aggregates by value.
- RISC-V ILP32: at most two `XLEN` words in `a0`/`a1`, everything else indirect.

A target without a classifier rejects by-value aggregates instead of assuming
the host ABI:

```text
error[T049]: aggregates by value are not classified for target 'wasm32-unknown-unknown';
pass scalars or pointers
```

Structs without `@Repr("C")`, `char`, sum types (`Option`, or a `Result` outside
the return position) and tuples
and fields that are themselves not C-safe are rejected with the same code.
Arrays are allowed as struct fields (`T campo[N]`) but not as parameters, where
they would silently decay to a pointer.

The header describes the target, not the host: `arandu build --emit=header
--target=thumbv6m-none-eabi` emits `_Static_assert(sizeof(void *) == 4)` and
32-bit struct sizes, so a consumer built for the wrong pointer model fails to
compile. The header is produced without choosing a backend, and two headers can
share a translation unit because the guard is derived from the export set.
Structs are emitted in dependency order, so a `@Repr("C")` struct nested by
value is complete before the struct that contains it.

C has a flat namespace, so the generator owns a small reserved prefix. A
`@Repr("C")` type named `AranduStr` (or starting with `AranduSlice`/
`AranduMutSlice`) is rejected: it would redeclare a generated typedef. Two
distinct types from different modules that map to the same C name are rejected
too, instead of letting one definition win silently.

## Linkage

`@Export` is the only permission to publish a symbol. Any other function
definition is emitted with internal linkage, so it is callable inside the
Arandu program but invisible to the linker; `main` stays visible. Marking a
function `public` changes Arandu-level visibility only, not the object file.
